# 软件架构分层模式对比

> **文档目的**：记录并对比两种主流的软件架构分层方法  
> **适用项目**：DesktopPet (C++/Qt6 桌面应用)  
> **创建日期**：2026-07-25  
> **参考来源**：SOLID原则、领域驱动设计(DDD)、Clean Architecture

---

## 一、传统分层架构 (Layered Architecture)

### 1.1 核心思想

**基于调用链顺序**的自顶向下分层方式，每一层只能调用其**直接下层**的服务。

- 📍 **历史背景**：源自 Java EE / .NET 的经典三层架构（MVC模式的延伸）
- 📍 **设计哲学**："UI → Business → Data" 的线性调用关系
- 📍 **核心理念**：关注点分离（Separation of Concerns），但保持简单的依赖方向

---

### 1.2 层级结构图

```
┌─────────────────────────────────────────────────────────────┐
│                    第1层：表现层 (Presentation)               │
│                                                             │
│   职责：用户界面展示与交互                                    │
│   组件：QML界面、ViewModel、Controller                       │
│   特点：最容易变化，不包含业务规则                             │
│   示例：Widgets/*.qml, CMainNoteListViewModel                │
├─────────────────────────────────────────────────────────────┤
│                    第2层：业务逻辑层 (Business Logic)          │
│                                                             │
│   职责：处理业务规则、工作流、状态管理                          │
│   组件：Service类、Use Case、Domain Service                   │
│   特点：包含核心业务价值，但可能混杂技术细节                    │
│   示例：CNoteBusiness, CAppSystem                            │
├─────────────────────────────────────────────────────────────┤
│                 第3层：数据访问层 / 适配器层 (Data Access)      │
│                                                             │
│   职责：封装CRUD操作、缓存策略、数据转换                        │
│   组件：Repository、DAO、Data Mapper、Cache                   │
│   特点：连接业务与技术实现，决定何时读写缓存/数据库             │
│   示例：CNoteDataService, NoteDataCache                      │
├─────────────────────────────────────────────────────────────┤
│                  第4层：基础设施层 (Infrastructure)            │
│                                                             │
│   职责：纯粹的技术实现（文件I/O、网络通信、外部API）           │
│   组件：File Reader/Writer、Database Driver、HTTP Client       │
│   特点：可替换性强，不包含任何业务逻辑                         │
│   示例：CNoteDataRW, CDataRWMgr, CDataSave              │
├─────────────────────────────────────────────────────────────┤
│                     第5层：基础层 (Foundation)                 │
│                                                             │
│   职责：核心数据类型、通用工具、基础接口定义                    │
│   组件：数据结构体、枚举、常量定义、基类                        │
│   特点：最稳定，被所有上层依赖                                 │
│   示例：ST_NOTE_DATA, datatype.h, DServiceBase.h            │
└─────────────────────────────────────────────────────────────┘
```

**依赖方向**：`第1层 → 第2层 → 第3层 → 第4层 → 第5层` （单向向下）

### 1.3 各层职责详细说明

#### 表现层 (Presentation Layer)
```cpp
/**
 * @brief 职责范围
 * - 接收用户输入事件（点击、输入）
 * - 将数据模型转换为可视化形式
 * - 验证用户输入的基本格式（非业务验证）
 * 
 * @note 不应包含：
 * - 业务规则的判断逻辑
 * - 数据持久化操作
 * - 复杂的状态管理
 */
class CMainNoteListViewModel : public QAbstractListModel {
    // ✅ 正确：数据绑定到QML
    // ✅ 正确：格式化显示文本（如时间戳转字符串）
    // ❌ 错误：判断笔记是否应该被保存（这是业务层的职责）
};
```

#### 业务逻辑层 (Business Logic Layer)
```cpp
/**
 * @brief 职责范围
 * - 实现业务规则和工作流程
 * - 协调多个数据访问对象
 * - 管理事务边界
 * 
 * @note 典型问题：
 * - 可能直接依赖具体的数据访问实现（如JdbcTemplate）
 * - 单元测试时难以Mock底层依赖
 */
class CNoteBusiness {
public:
    void SaveNote(const ST_NOTE_DATA& noteData) {
        // ✅ 正确：业务规则验证
        if (!ValidateNoteContent(noteData.m_szContent)) {
            throw std::invalid_argument("内容不合法");
        }
        
        // ✅ 正确：调用数据访问层执行持久化
        m_pDataService->SaveNoteData(noteData);
        
        // ✅ 正确：触发业务事件（如通知、日志）
        EmitNoteSavedEvent(noteData.m_s32id);
    }
    
private:
    std::shared_ptr<CNoteDataService> m_pDataService;  // 依赖下层
};
```

#### 数据访问层 (Data Access Layer)
```cpp
/**
 * @brief 职责范围
 * - 封装具体的CRUD操作
 * - 实现缓存策略（读缓存、写失效）
 * - 数据对象映射（ORM或手动转换）
 * 
 * @note 关键作用：
 * - 作为业务层与技术实现的缓冲区
 * - 决定性能优化策略（批量读取、懒加载）
 */
class CNoteDataService {
public:
    void ReadNoteData(const std::string& fileName, std::vector<ST_NOTE_DATA>& data) {
        // ✅ 正确：先查缓存（Cache-Aside模式）
        auto cached = m_pCache->get();
        if (cached && !cached->empty()) {
            data = *cached;
            return;  // 缓存命中，直接返回
        }
        
        // ✅ 正确：缓存未命中，回退到基础设施层
        m_pRW->ReadNoteData(fileName, data);
        
        // ✅ 正确：更新缓存
        m_pCache->update(data);
    }
    
private:
    std::shared_ptr<NoteDataCache> m_pCache;     // 缓存组件
    std::unique_ptr<CNoteDataRW> m_pRW;          // 文件读写组件
};
```

#### 基础设施层 (Infrastructure Layer)
```cpp
/**
 * @brief 职责范围
 * - 纯粹的技术实现细节
 * - 与外部系统交互（文件系统、数据库、网络）
 * - 不包含任何业务语义
 * 
 * @设计原则：
 * - 应该是可插拔的（Pluggable）
 * - 替换不影响上层业务代码
 */
class CNoteDataRW {
public:
    void ReadNoteData(const std::string& fileName, std::vector<ST_NOTE_DATA>& data) {
        // ✅ 正确：纯粹的文件I/O操作
        std::ifstream file(fileName, std::ios::binary);
        
        // 读取文件头...
        // 读取数据记录...
        // 填充data向量...
    }
    
    /**
     * @note 这个类不应该知道：
     * - 缓存的存在（那是上层的职责）
     * - 业务规则（如内容长度限制）
     * - 其他模块的存在（如CNoteDataService）
     */
};
```

### 1.4 典型代码示例（完整调用链）

#### 场景：用户点击"保存笔记"按钮

```cpp
// ==================== 第1层：表现层 ====================
// 文件: Widgets/content/PopInputNoteDia.qml
// 或: Services/WidgetServices/MainWidget/CMainNoteListViewModel.cpp

void CMainNoteListViewModel::onSaveButtonClicked() {
    ST_NOTE_DATA noteData;
    noteData.m_s32id = GenerateNewId();
    strncpy(noteData.m_szContent, m_content.toUtf8().constData(), 
            NoteSpace::CONTENT_LENGTH_MAX);
    noteData.m_eNoteLevel = E_NOTE_EVENT_WAKEUP_LEVEL_NORMAL;
    
    // ↓ 调用业务层
    m_noteBusiness->SaveNote(noteData);
}

// ==================== 第2层：业务逻辑层 ====================
// 文件: Services/Module/BusinessModule/CNoteBusiness/CNoteBusiness.cpp

void CNoteBusiness::SaveNote(const ST_NOTE_DATA& noteData) {
    // 业务规则1：检查内容是否为空
    if (strlen(noteData.m_szContent) == 0) {
        throw std::runtime_error("笔记内容不能为空");
    }
    
    // 业务规则2：检查ID是否已存在
    if (IsDuplicateId(noteData.m_s32id)) {
        throw std::runtime_error("笔记ID重复");
    }
    
    // 业务规则3：设置时间戳
    auto now = time(nullptr);
    noteData.m_tWriteTime = now;
    noteData.m_tModifyTime = now;
    
    // ↓ 调用数据访问层
    m_dataService->SaveNoteData("notes.dat", noteData);
    
    // 业务后续操作：发送通知、更新统计
    NotifyObservers(NoteEvent::SAVED, noteData.m_s32id);
}

// ==================== 第3层：数据访问层 ====================
// 文件: Services/Module/Adapter/DataManager/CNoteDataService.cpp

void CNoteDataService::SaveNoteData(
    const std::string& strNoteFileName, 
    const ST_NOTE_DATA& noteData, 
    INT32 s32AppendPos) 
{
    std::lock_guard<std::mutex> lock(m_mutex);
    
    // 缓存失效策略（Write-Through或Write-Behind）
    m_pCache->invalidate();  // 清除过期缓存
    
    // ↓ 调用基础设施层
    m_pRW->SaveNoteData(strNoteFileName, noteData, s32AppendPos);
}

// ==================== 第4层：基础设施层 ====================
// 文件: Services/Module/Other/DataReadWriter/CNoteDataRW.cpp

void CNoteDataRW::SaveNoteData(
    const std::string& strNoteFileName, 
    const ST_NOTE_DATA& noteData, 
    INT32 s32AppendPos) 
{
    // 纯粹的文件写入操作
    d_ptr->m_pDataSaveRWMgr->Write2FileData(
        strNoteFileName,
        reinterpret_cast<const char*>(&noteData),
        sizeof(ST_NOTE_DATA),
        s32AppendPos
    );
}
```

### 1.5 适用场景与优缺点

#### ✅ 优点
| 优势 | 说明 |
|------|------|
| **简单直观** | 符合人类的线性思维习惯，学习成本低 |
| **职责清晰** | 每一层有明确的边界和单一职责 |
| **易于理解** | 新团队成员可以快速上手 |
| **工具支持好** | IDE、框架对这种模式有完善的支持 |

#### ❌ 缺点
| 劣势 | 说明 |
|------|------|
| **业务泄露** | 业务逻辑可能渗透到表现层或数据层 |
| **测试困难** | 测试业务层时需要Mock整个调用链 |
| **变更代价高** | 更换数据库时要修改业务层代码 |
| **循环依赖风险** | 大型项目中容易出现隐式依赖 |

#### 🎯 适用场景
- ✅ 小型到中型项目（代码量 < 50K行）
- ✅ CRUD为主的简单业务系统
- ✅ 团队经验较少，追求快速交付
- ✅ 技术栈稳定，短期内不会更换

## 二、洋葱架构/六边形架构 (Onion/Hexagonal Architecture)

### 2.1 核心思想（基于DIP原则）

**基于稳定性**的向内分层方式，核心思想来自 SOLID 原则中的**依赖倒置原则（DIP）**：

> **高层模块不应该依赖低层模块，两者都应该依赖其抽象**  
> —— Robert C. Martin (Uncle Bob)

- 📍 **理论基础**：领域驱动设计（DDD）、Clean Architecture (Robert C. Martin)
- 📍 **设计哲学**："业务是核心，技术只是实现手段"
- 📍 **核心理念**：越靠近中心的部分越稳定，越不容易变化

---

```

                         │         外部圈层 (External)      │
                         │                                 │
                         │  ┌───────────────────────────┐  │
                         │  │  UI框架 (Presentation)    │  │
                         │  │  • QML/Qt Widgets         │  │

                         │  │  基础设施 (Infrastructure) │  │
                         │  │  • File I/O               │  │
                         │  │  • Database Driver        │  │
                         │  │  • External API Clients   │  │
                         │  │  • Message Queue          │  │
                         │  └───────────┬───────────────┘  │
                         └──────────────┼──────────────────┘
                                    依赖接口 (Interfaces)
                                    向内指向
                    ┌───────────────▼───────────────────┐

                    └───────────────┬───────────────────┘
```

### 2.3 各层职责详细说明

#### 外部圈层 (Outer Layers)

##### UI框架 (Presentation Mechanism)
```cpp
/**
 * @brief 职责范围
 * - 仅负责如何展示数据（渲染机制）
 * - 如何接收用户输入（交互机制）
 * 
 * @关键区别于传统架构：
 * - 这里不包含ViewModel的业务逻辑
 * - ViewModel应该属于应用服务层或更内层
 * - UI只依赖"展示接口"，不依赖具体业务类
 */

// 定义展示接口（在领域层或应用层）
struct INotePresenter {
    virtual void DisplayNotes(const std::vector<ST_NOTE_DATA>& notes) = 0;
    virtual void ShowError(const std::string& message) = 0;
};

// UI实现（在外部层）
class QmlNotePresenter : public INotePresenter {
    void DisplayNotes(const std::vector<ST_NOTE_DATA>& notes) override {
        // 转换为QML可识别的格式并发送信号
        emit notesUpdated(ConvertToQVariantList(notes));
    }
};
```

##### 基础设施 (Infrastructure)
```cpp
/**
 * @brief 职责范围
 * - 实现领域层定义的技术接口
 * - 可插拔的技术实现
 * 
 * @关键设计原则：
 * - 必须依赖抽象接口，不能反向依赖
 * - 可以随时替换而不影响业务代码
 */

// 定义持久化接口（在领域层）
interface INoteRepository {
    virtual void Save(const ST_NOTE_DATA& data) = 0;
    virtual std::vector<ST_NOTE_DATA> LoadAll() = 0;
    virtual void Delete(INT32 id) = 0;
};

// 文件系统实现（在外部层/基础设施层）
class FileNoteRepository : public INoteRepository {
public:
    explicit FileNoteRepository(std::string basePath) 
        : m_basePath(std::move(basePath)) {}
    
    void Save(const ST_NOTE_DATA& data) override {
        // 纯粹的文件I/O，不知道业务规则
        std::ofstream file(m_basePath + "/notes.dat", 
                          std::ios::binary | std::ios::app);
        file.write(reinterpret_cast<const char*>(&data), 
                  sizeof(ST_NOTE_DATA));
    }
    
private:
    std::string m_basePath;
};

// 未来可以轻松替换为数据库实现
class DatabaseNoteRepository : public INoteRepository {
    // 使用SQLite/PostgreSQL实现相同接口
};
```

#### 应用服务层 (Application Services)
```cpp
/**
 * @brief 职责范围
 * - 编排领域对象的协作流程
 * - 管理事务边界
 * - 协调基础设施与领域层
 * 
 * @重要特征：
 * - "薄"层：本身不包含复杂业务规则
 * - 类似于导演的角色：指挥各个演员（领域对象）表演
 * - 是外部世界进入领域核心的唯一入口
 */

class NoteApplicationService {
public:
    // 通过构造函数注入依赖（依赖注入 DI）
    NoteApplicationService(
        std::shared_ptr<INoteRepository> repository,  // 持久化接口
        std::shared_ptr<INotePresenter> presenter,    // 展示接口
        std::shared_ptr<INoteValidator> validator     // 验证接口
    ) : m_repository(std::move(repository))
      , m_presenter(std::move(presenter))
      , m_validator(std::move(validator))
    {}
    
    void HandleSaveNoteCommand(const SaveNoteRequest& request) {
        // 1. 应用层编排：组装领域对象
        ST_NOTE_DATA noteData = BuildNoteFromRequest(request);
        
        // 2. 委托给领域层进行业务验证
        auto validationResult = m_validator->Validate(noteData);
        if (!validationResult.IsValid()) {
            m_presenter->ShowError(validationResult.GetError());
            return;
        }
        
        // 3. 委托给领域层执行业务规则
        ApplyBusinessRules(noteData);
        
        // 4. 通过接口调用基础设施（不知道具体实现）
        m_repository->Save(noteData);
        
        // 5. 通知展示层更新
        auto allNotes = m_repository->LoadAll();
        m_presenter->DisplayNotes(allNotes);
    }
    
private:
    std::shared_ptr<INoteRepository> m_repository;
    std::shared_ptr<INotePresenter> m_presenter;
    std::shared_ptr<INoteValidator> m_validator;
};
```

#### ⭐ 领域层 (Domain Core) - 最重要！

```cpp
/**
 * @brief 职责范围
 * - 定义核心业务模型（Entity）
 * - 实现业务规则（Domain Service/Specification）
 * - 定义值对象（Value Object）
 * - 声明领域事件（Domain Event）
 * 
 * @黄金法则：
 * - 零外部依赖！（不依赖任何框架、库、技术实现）
 * - 可以独立编译运行（Pure C++ / Pure Java）
 * - 这里的代码是最有价值的资产
 */

// ==================== Entity（实体）====================
#pragma pack(push, 1)
struct ST_NOTE_DATA {
    // --- 基础信息 ---
    INT32                           m_s32id;                    ///< 便签唯一标识 ID (主键)
    char                            m_szContent[NoteSpace::CONTENT_LENGTH_MAX]; ///< 内容
    
    // --- 分类与等级 ---
    E_NOTE_EVENT_WAKEUP_LEVEL       m_eNoteLevel;               ///< 重要程度等级
    E_NOTE_EVENT_TYPE               m_eEventType;               ///< 事件类型
    
    // --- 时间信息 ---
    time_t                          m_tWriteTime;               ///< 创建时间
    time_t                          m_tModifyTime;              ///< 最后修改时间
    
    // --- 提醒相关 ---
    time_t                          m_tRemindTime;              ///< 提醒时间
    E_REMIND_TYPE                   m_eRemindType;              ///< 提醒类型
    
    // --- 状态标志 ---
    BOOL                            m_bIsCompleted;             ///< 是否已完成
    BOOL                            m_bIsDeleted;               ///< 是否已删除
    
    // --- 扩展指针数组 ---
    st_NoteEvent                    *m_pstNoteEvents[NoteSpace::NOTE_DATA_EVENT_COUNT]; ///< 关联事件
    VOID                            *m_pReserved[FixedValueSpace::RESERVED_COUNT]; ///< 预留指针
};
#pragma pack(pop)

// ==================== Domain Service（领域服务）====================
class NoteDomainService {
public:
    /**
     * @brief 判断笔记是否应该被自动删除
     * @param note 笔记实体
     * @param currentTime 当前时间戳
     * @return true 如果满足自动删除条件
     * 
     * @note 这是纯业务规则，不涉及任何技术实现
     */
    bool ShouldAutoDelete(const ST_NOTE_DATA& note, time_t currentTime) const {
        // 规则1：已删除且超过30天
        if (note.m_bIsDeleted && 
            (currentTime - note.m_tModifyTime) > 30*24*3600) {
            return true;
        }
        
        // 规则2：已完成且超过1年未修改
        if (note.m_bIsCompleted && 
            (currentTime - note.m_tModifyTime) > 365*24*3600) {
            return true;
        }
        
        return false;
    }
    
    /**
     * @brief 计算笔记的重要程度得分
     * @return 得分范围 [0, 100]
     */
    int CalculateImportanceScore(const ST_NOTE_DATA& note) const {
        int score = 0;
        
        // 根据紧急程度加分
        switch (note.m_eNoteLevel) {
            case E_NOTE_EVENT_WAKEUP_LEVEL_IMPORTANT_URGENT:
                score += 40;
                break;
            case E_NOTE_EVENT_WAKEUP_LEVEL_URGENT:
                score += 30;
                break;
            case E_NOTE_EVENT_WAKEUP_LEVEL_IMPORTANT:
                score += 20;
                break;
            default:
                score += 10;
        }
        
        // 根据事件类型调整
        switch (note.m_eEventType) {
            case E_NOTE_EVENT_WORK:
                score += 15;
                break;
            case E_NOTE_EVENT_STUDY:
                score += 10;
                break;
            default:
                break;
        }
        
        // 时间紧迫性因子
        if (note.m_tRemindTime > 0) {
            time_t now = time(nullptr);
            double hoursUntilRemaind = difftime(note.m_tRemindTime, now) / 3600.0;
            
            if (hoursUntilRemaind < 24) score += 25;      // 24小时内
            else if (hoursUntilRemaind < 72) score += 15;  // 3天内
            else if (hoursUntilRemaind < 168) score += 5;  // 1周内
        }
        
        return std::min(score, 100);  // 上限100分
    }
};
```

### 5.3 关键要点备忘

#### 📌 传统分层架构要点
- ✅ 基于**调用链顺序**分层
- ✅ 依赖方向：**自顶向下**
- ✅ 适合：**小型项目、快速原型、初级团队**
- ❌ 缺点：**业务与技术耦合、测试困难**

#### 📌 洋葱/DIP架构要点
- ✅ 基于**稳定性**分层（稳定的在内，变化的在外）
- ✅ 依赖方向：**向内依赖（依赖抽象）**
- ✅ 适合：**复杂业务、长期项目、高级团队**
- ❌ 缺点：**学习成本高、可能过度设计**

#### 📌 DesktopPet 当前策略
- **现状**：处于传统分层与洋葱架构的混合状态
- **问题**：存在依赖倒置（DataReadWriter依赖DataManager）
- **方案**：先修复依赖问题，再考虑是否需要完整重构
- **原则**：**YAGNI** (You Aren't Gonna Need It) - 不过度设计
